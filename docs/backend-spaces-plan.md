# Back-end plan: spaces

The app-service (`backend/app-service`) already has full space management: list, read, create, update and delete, with roles, validation and French error messages. This plan finishes the spaces part of the back end for the first deliverable: a code clean-up, a correct status for "space has bookings", and the search for free spaces. Bookings and users get their own plans later.

How the back end is built (file structure, layers, data flows, endpoints, schema) is described in `backend/app-service/README.md`.

Each step starts with tests where code changes, ends with all tests passing (back end, and front end when it is touched), and is committed on its own.

## Starting point

- **Done:** `/api/spaces` (CRUD), `/api/me`, the fixed placeholder user and role, CORS for the React app, 42 back-end tests.
- **Already in the database but unused:** the `bookings` table and the `Booking` entity. No repository, service or endpoint uses them yet.
- **Not done:** the free-space search (`GET /api/spaces/available`), which the front end already calls (it answers "Pas encore disponible" in real mode); 409 for "space has bookings" (currently 500); small leftovers in the code.

## Free-space search

What the front end already expects (`src/lib/api.js`, mock in `src/lib/mock/handlers.js`):

- **Request:** `GET /api/spaces/available?start=2026-12-01T09:00&end=2026-12-01T13:00&type=ROOM`. `start` and `end` are local date-times (ISO, no time zone); `type` is optional.
- **Answer:** 200 with the list of spaces (same JSON as `GET /api/spaces`) that have no booking overlapping the slot, filtered by type if given.
- **Overlap rule (same as `overlaps` in `src/lib/dates.js`):** a booking overlaps when `booking.start < end` and `start < booking.end`. Bookings that only touch the slot (one ends at 13:00, the slot starts at 13:00) do not block it.
- **Access:** open to everyone, guests included (spec: "Recherche d'espaces disponibles" is a visitor feature). `GET /api/spaces/**` is already open in `SecurityConfig`.

Files:

| Layer | Change |
| --- | --- |
| `repository/SpaceRepository` | A JPQL query: spaces of the type (or all if no type) for which no booking exists with `b.space = s and b.startDateTime < :end and b.endDateTime > :start`. One query, no `BookingRepository` needed yet |
| `service/SpaceService` | `findAvailable(start, end, type)`: checks that `end` is after `start`, then calls the repository |
| `controller/SpaceController` | `@GetMapping("/available")` with `@RequestParam` `start`, `end` (`LocalDateTime`, ISO) and optional `type` (`Space.SpaceType`). The fixed path `/available` takes priority over `/{id}` |
| `controller/GlobalExceptionHandler` | Missing parameter (`MissingServletRequestParameterException`) → 400 `Données invalides` with `errors: { start: "Champ obligatoire" }`, like the mock. Wrong value (`MethodArgumentTypeMismatchException`, bad date or unknown type) → 400 with `"Valeur invalide"` on that parameter |
| New service exception | End not after start → 400 `Données invalides` with `errors: { end: "La fin doit être après le début" }` |

Tests, written first (numbers follow in the test lists):

- Repository (`@DataJpaTest`, real MariaDB, bookings saved with `TestEntityManager`): a booked space is left out; a free space is returned; a booking that only touches the slot does not block it; the type filter works; no type returns every type.
- Service (Mockito): the repository result is returned; end before or equal to start is refused without calling the repository.
- Controller (`@WebMvcTest`): 200 with the list; 200 for a guest; 400 for a missing `start`, a bad date, an unknown type, and end before start.
- Integration (`@SpringBootTest`): a space with a booking in the slot is not in the answer; the same space is in it for another slot.

## Decisions

- **Opening hours:** for the first deliverable they stay fixed in the front end (`src/lib/config.js`). The search does not check them: the front end only sends slots inside opening hours. Admin management of hours (spec: "gérer les horaires") and a back-end check are listed in `to-do.md`.
- **Search query in `SpaceRepository`:** the answer is a list of spaces, so the query belongs with them. A `BookingRepository` comes with the bookings plan.
- **End after start:** the back end refuses an empty or reversed slot, which the mock does not check. The mock gets the same check in step 4 so that both modes answer the same way.
- **No new migration:** the foreign key on `bookings.space_id` already gives an index for the search; a combined index on (`space_id`, `start_date_time`) can wait until there are many bookings.
- **Migration names:** `V1__init.sql` to `V3__init.sql` keep their names. Flyway has already applied them, and renaming them would break existing databases.

## Out of scope (later)

- **Bookings plan:** `BookingRepository`, booking endpoints (list, mine, create, update, cancel), price calculation, opening-hours and cancellation rules on the back end, concurrent bookings of the same slot (spec: concurrent access handled by the database).
- **Users plan:** auth-service, JWT instead of `PlaceholderAuthenticationFilter`, first name in `/api/me`, admin management of accounts.
- **Spaces, not needed for the first deliverable:** sites (multi-site is a potential extra in the spec), pagination of the space list, admin management of opening hours.
- **Known limit:** `SpaceService.update` reads then saves in two separate transactions, so two admins saving the same space at once means the last save wins. Acceptable with one admin; revisit with `@Transactional` or a version column if needed (`delete` then needs the change described in its comment).
- Deployment: see `to-do.md`.
